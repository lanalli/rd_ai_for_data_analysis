# CLAUDE.md — Payments data quality workflow

Guidance for working in this project (`payments/`). Keep changes reproducible and auditable.

## Project structure
```
payments/
  payments.csv                    # RAW source — never modified
  payments_clean.csv              # cleaned output (regenerated by the cleaning script)
  reports/
    data_quality_audit.md         # findings: problems, risks, reporting/integration threats
    cleaning_log.txt              # run log from the last cleaning pass
  rules/
    cleaning_rules.md             # one rule each: check → action → changed columns → validation
```
Audits go in `reports/`, rules in `rules/`, cleaned data at the project root beside the raw file. Do not scatter outputs elsewhere.

## Profiling and cleaning order
1. **Profile first** on the raw file (shape, dtypes, nulls, distinct values, formats, duplicates, outliers, relationships). Write findings to `reports/data_quality_audit.md`.
2. **Define rules** in `rules/cleaning_rules.md` from the audit findings — never clean ad hoc.
3. **Clean** only after the audit and rules exist, producing `payments_clean.csv`.
4. **Validate** the cleaned output against every rule before reporting done.
Never clean before profiling; never invent a cleaning step that isn't a documented rule.

## Working with raw data
- Treat `payments.csv` as read-only. Load it, don't overwrite it.
- Cleaning always writes a **new** file (`payments_clean.csv`); the raw file stays intact so the pipeline is re-runnable from source.
- Only **confirmed defects** (audit §1) may change data. **Potential issues / censoring** (audit §2 — e.g. partial trailing month, early cohort) are documented as advisory rules, not silently altered.
- Refunds and other real events are **kept**; handle their impact with derived columns (e.g. `net_amount_usd`), not by deleting rows.

## Confirm before removing or deleting anything
- **Ask the user before** deleting rows/columns, dropping records, or overwriting any existing file — including replacing the raw file. State what will be removed and how many records.
- Before removing "duplicate" rows, prove they are duplicates (e.g. the base id already exists with matching fields) and report the count.
- Never delete files on disk without explicit confirmation.

## Scripts and validation
- All cleaning is done by a **script** (Python/pandas), not manual edits, so it is repeatable.
- The script must **log** what it changed (rows in/out, rows removed and why, columns changed) to `reports/cleaning_log.txt`.
- Every rule in `cleaning_rules.md` records: **check condition · action on violation · changed columns · validation check**.
- A separate **validation pass** must confirm, after cleaning: raw file unchanged; expected row/column counts; formats and types valid; no nulls introduced; derived columns correct; no rows fabricated (all cleaned ids exist in the raw file); exactly the intended rows removed. Report done only when all checks pass.

## Prohibited actions
- Do **not** modify or overwrite `payments.csv`.
- Do **not** delete rows, columns, or files without confirming with the user first.
- Do **not** clean before profiling, or apply undocumented cleaning steps.
- Do **not** drop refunded or otherwise real records to "simplify" revenue — use net/derived columns.
- Do **not** sum `amount_usd` as revenue without the refund rule (use `net_amount_usd`).
- Do **not** report success without running the validation pass.
