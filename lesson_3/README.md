# Lesson 3 — Payments Data Quality Workflow

A reproducible data-quality workflow for a subscription **payments** dataset: profile the raw file, document cleaning rules, produce a cleaned dataset, and validate the result — with the raw source never modified and every step scripted and auditable.

## What this does

Given `payments.csv` (87,924 subscription payment records), the workflow:

1. **Profiles** the raw file for structure, types, completeness, consistency, duplicates, outliers, and relationship integrity.
2. **Documents** each data-quality rule (check → action → changed columns → validation).
3. **Cleans** the data into a new file, applying only confirmed-defect rules.
4. **Validates** the output against every rule, separating *confirmed issues* from *assumptions*.

## Dataset

| Column | Description |
|---|---|
| `payment_id` | Payment identifier, format `P` + 8 digits |
| `user_id` | User identifier, format `U` + 7 digits |
| `paid_at` | Payment date (`YYYY-MM-DD`), range 2021-01-01 → 2023-02-26 |
| `amount_usd` | Charge amount (monthly = $49, annual = $399) |
| `plan` | `monthly` or `annual` |
| `is_refunded` | `0` / `1` refund flag |

`payments_clean.csv` adds a derived **`net_amount_usd`** (equal to `amount_usd`, or `0` when refunded) so realized revenue is directly summable.

## Usage

Requires Python 3 with `pandas` (`pip install pandas`).

```bash
# Validate the raw source (read-only) — writes reports/validation_report.md
python scripts/validate_dataset.py --data payments.csv

# Validate the cleaned file (expect all checks to pass)
python scripts/validate_dataset.py --data payments_clean.csv

# Regenerate the cleaned file, then re-validate it
python scripts/validate_dataset.py --data payments.csv --clean --yes \
       --out-data payments_clean.csv
```

The script exits `0` only when every confirmed-issue rule passes, so it works as a CI or pipeline gate. `--clean` requires `--yes` and never overwrites the source.

## Key findings (raw data)

The dataset is internally very regular, with a small set of injected defects that quietly distort revenue and user metrics:

- **40 shadow-duplicate payments** (`payment_id` ending `_X`, all on sentinel user `U9999999`) that double-count real payments — inflating revenue by $3,360 and volume by 40.
- **Refunds carry positive amounts** with no net/signed value: summing `amount_usd` overstates realized revenue by $115,003 (1,597 refunds).
- **Right-censored final month** (Feb 2023) reads as a false ~30% decline; **left-censored** first month (2021-01) hides early-user tenure.

Naïve `SUM(amount_usd)` = **$6,393,226**; true net realized revenue = **$6,274,863**.

Full detail in [`reports/data_quality_audit.md`](reports/data_quality_audit.md).

## Cleaning rules (summary)

| Rule | Check | Action |
|---|---|---|
| R1 | `payment_id` malformed (`_X`) & duplicates a valid base id | remove row |
| R2 | `payment_id` matches `^P\d{8}$` and is unique | enforce / quarantine |
| R3 | no sentinel user `U9999999`; `user_id` well-formed | remove row |
| R4 | `amount_usd` numeric, `is_refunded` ∈ {0,1}, `paid_at` valid date | cast types |
| R5 | refund-safe revenue via `net_amount_usd` | add derived column |
| R6 | plan ↔ price coherence (monthly=$49, annual=$399) | flag for review |

Censoring and scope/currency questions are documented as **advisory** rules — reported, not silently altered. Full rules in [`rules/cleaning_rules.md`](rules/cleaning_rules.md).

## Principles

- The raw file is read-only; cleaning always writes a new file.
- Only confirmed defects change data; row removal requires confirmation.
- Confirmed issues are kept separate from assumptions.
- Every run is scripted, logged, and gated by a validation pass.

See [`CLAUDE.md`](CLAUDE.md) for the full working conventions.
